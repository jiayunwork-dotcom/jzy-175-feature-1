# 精确求解与增量重解说明

面向规划科同事的三个老问题，本设计的立场先摆在这里：

1. **贪心凑出的结果绝不标成最优。** 贪心只用来产生初始上界；
   `proven_optimal=True` 只可能由分支定界完整证明给出。
2. **有点漏覆盖绝不可能报成功。** 所有返回的开站组合都在返回前
   按位掩码核对全覆盖；全开都够不着时直接判无解并列漏点。
3. **增量结果必须和全量对得上。** 增量路径与全量路径跑的是同一个
   精确求解器，差别只在"初始上界"，因此最优站数与方案完全等价。

---

## 1. 问题形式化

平面上居民点集合 `R`、候选站址集合 `S`、统一半径 `r`。

- 站 j 覆盖居民点 i ⇔ 欧氏距离 `d(i,j) ≤ r`（边界算覆盖）；
- 每座站费用 1，目标：在满足"每个居民点至少被一座开站覆盖"的前提下，
  使开站数最少；
- 另有必开集合 `F ⊆ S`，任何可行解都必须包含 F。

这就是无权**集合覆盖**（NP 难）。几何只用于一次性构建覆盖关系，
之后全部按位掩码做纯组合求解，与坐标单位无关（单位固定即可）。

## 2. 覆盖关系构建（`app/coverage.py`）

对每一对 (居民点, 站) 比较平方距离与 `r²`，得到：

- `by_station[j]`：站 j 覆盖的居民点位掩码；
- `coverers[i]`：能覆盖居民点 i 的站位掩码。

复杂度 O(|R|·|S|)。同坐标居民点在**求解器入口**折叠为唯一居民点，
所以重复坐标天然不影响站数（漏点列表再映射回原始编号）。

## 3. 精确求解器（`app/solver.py`）

### 3.1 预处理

1. **同坐标折叠**：唯一坐标参与求解，原下标保留用于结果回映。
2. **全开可达性**：任何居民点若 `coverers[i]=0`，立即判无解，
   一次性列出全部够不着的点（不必进入搜索）。
3. **支配列消除（仅根节点一次）**：若站 j 的覆盖集是站 k 的子集，
   删掉 j 不会改变最优值（任何选 j 的方案都可用 k 替代，费用相同）。
   **强制站永不参与消除**，保证必开约束不被破坏。
4. **初始可行上界**：
   - 贪心（选当前覆盖未覆盖点最多的站，平局取下标小者）从必开站出发补齐；
   - 若调用方给了热启动种子（增量复用），从种子再贪心补齐，取更优者。

贪心解只放进 `best`（上界），**永远不会**据此宣称最优。

### 3.2 节点归约：强制传播

在子问题中，若某个未覆盖居民点在"剩余可用站"里只有唯一覆盖者，
该站必选，直接选入；若一个未覆盖点已经没有任何可用站，剪枝。
这个归约反复执行到不动点，且本身是安全的（不改变子问题可行性/最优值）。

### 3.3 两个合法下界

在每个子问题（已选 k 座，未覆盖集合 U，可用站 A）上计算"至少还需几座"：

- **打包下界**：贪心地取一个居民点 i，删掉所有与 i 共享任一可用站的
  居民点，再取下一个……取出的居民点两两不可能由同一座站覆盖，
  计数即合法下界（实现里取"可用覆盖站最少"的点，使打包尽量大）。
- **最大覆盖反推下界**：把可用站在 U 上的覆盖增益降序排列，
  前 s 大之和是"s 座站最多能新覆盖多少行"的宽松上界；从 s=1
  累加，直到累计行数 ≥ |U|，此时的 s 即合法下界。

两者取大，再加上已选站数 k。两个都是合法下界，所以
**任何时刻（含超时）报告的 `lower_bound` 都 ≤ 真实最优**。

### 3.4 分支

- 选"可用覆盖站数最少"的未覆盖居民点（平局选其覆盖站能联合盖住
  最多未覆盖点的居民点）——这是集合覆盖里经典的最强约束变量。
- 对能覆盖它的站逐一生成"选入该站"的子节点（include-only k 叉分支）。
  "不选某站"并不需要显式分支：它由"选了另一座能覆盖该居民点的站"
  的兄弟分支隐含，整棵树仍然完整枚举了所有最小覆盖（可能重复，
  但不影响正确性，剪枝会兜住）。
- 子节点先做 3.2 归约、算 3.3 下界；立即满足全盖的叶节点更新 `best`；
  `k+lb_add ≥ best` 的子节点直接剪枝。

### 3.5 搜索顺序与"已探索规模 / 下界"

深度优先（DFS）控制内存（栈深线性），但每层的兄弟节点预先按 LB
升序放在一个小顶堆里。维护一个**全局最小堆**，其堆顶是所有未处理
兄弟节点里最小的 LB——这就是进度接口里的已证明下界：

- 堆顶 LB ≥ 当前 best ⇒ 所有活节点都不可能更优 ⇒ **证明最优**；
- 搜索树自然穷尽（栈空）⇒ 同样证明最优；
- 其余时刻 LB 始终合法（它是某个具体未探索节点的下界）。

进度每探索 256 个节点（可调）回调一次：
`explored_nodes / best_count / lower_bound`。

### 3.6 时限与取消（协作式）

- `time_limit`：用 `perf_counter` 的截止时刻，在主循环顶部与
  **根下界算完之后**检查。所以即使 `time_limit` 取极小正值，
  也能在完成全部预处理（含得到可行贪心解、算出根 LB）后立刻
  以 `timeout` 退出，交出 best 与合法 LB，而不是抛错。
- `cancel_event`：同样的检查点轮询，置位后以 `cancelled` 退出。
- 超时/取消结果带 `gap = best - lower_bound`，且 `proven_optimal=False`。
  哪怕 best 数值恰好等于真实最优，只要没完成证明就不标最优。

> 下界三明治（已被测试固化）：
> 超时报的 `lower_bound ≤ OPT ≤ best_count`，且 `chosen` 经位掩码
> 核对满足全覆盖。

### 3.7 作业状态与求解状态的对应

求解器状态 `optimal / infeasible` 映射为作业 `completed`；
`timeout / cancelled` 同名映射。无解是**正常完成的终态结果**
（不是失败），结果体里带 `uncovered`。

## 4. 增量重解（`app/incremental.py`）

### 4.1 采用的策略：热启动 + 完整证明

高频操作是"在某版本上增删几个居民点再求一次"。我们**没有**采用
"在旧最优解上局部修补后直接宣布最优"——那种做法要重新证明修补后
解的最优性，逻辑上等于把 B&B 再写一遍且极易出"增量与全量对不上"
的事故。

实际做法：

1. 若可复用，把**父版本已证明最优的开站集合**作为 `warm_stations`
   种子交给同一个精确求解器；
2. 求解器用它算出一个高质量初始上界（种子若已覆盖全部新点，
   上界就是旧站数；否则从种子贪心补几座）；
3. 之后分支定界**照常完整运行到证明最优**（或超时/取消）。

复用只影响"从多高的上界开始剪枝"，不影响可行性与最优性的任何判定。
因此增量解的站数与方案，与对同一版本数据从头求解**严格一致**；
全覆盖由求解器统一核验。作业结果里的 `strategy` 字段标注
`warm`（复用了种子）或 `cold`（退回全量）。

### 4.2 为什么不复用/差量化覆盖关系

覆盖构建是 O(|R|·|S|)，上千点也是毫秒级；差量缓存覆盖掩码却是
"增删后掩码错位"这类 bug 最容易藏身的地方，收益小、风险大。
故每次都用新数据完整重建覆盖关系，把复用严格限制在"一个初始上界"
这一个最不容易出错的点上。真正省下的计算量来自更紧的初始上界
带来的剪枝（居民点小改时，最优值通常不变或只差 1，搜索很快收敛）。

### 4.3 什么时候必须退回全量重解（`prepare_warm` 返回 None）

满足任一条即 `cold`：

- 半径变化（旧覆盖关系失效）；
- 候选址增删或坐标变化（旧站下标可能失效；当前 derive 接口只允许
  改居民点，但提交全新版本时候选址可以变，这里统一防御）；
- 必开站集合变化；
- 父版本没有"已证明最优"的可行方案（只有超时/取消结果时不复用）；
- 旧站下标在新版本中找不到（防御性）。

另外作业层还有一层兜底：热启动路径抛任何异常，都会自动用
`warm_stations=None` 重跑一次全量求解，正确性永远优先于性能。

### 4.4 对拍策略（对应你要做的随机增删对拍）

测试 `test_incremental_matches_full_on_random_edits` 生成
"居民点围绕站抖动"的可行实例，从父版本最优解出发做 60 步随机
增/删/混合操作，每步比较：

- 增量站数 == 全量站数；
- 状态一致；最优时 `proven_optimal` 一致；
- 增量 `chosen` 对新居民点集合位掩码全覆盖。

`test_random_matches_brute_force` 另在 200 组随机小实例上
直接与枚举暴力对拍站数与可行性。

## 5. 半径单调性

半径只调大时，每个站的覆盖集只增不减，可行解集合是上一轮的超集，
故最优站数单调不增——这由集合覆盖的结构天然保证，求解器不做
任何特判。半径扫描作业因此可预期得到不增的站数阶梯（测试已固化）。

## 6. 复杂度与规模

- 最坏情况指数级（NP 难），工程规模上靠支配列消除、强制传播、
  双下界与最强约束分支把证明时间压下来；本仓库难例（120 居民/60 站、
  每点 3~6 个覆盖者）完整证明约数秒，超时/取消路径保证随时可交出
  有界结果。
- 位掩码用 Python 大整数，居民点数没有硬性上限；实际受 B&B 搜索量
  而非掩码宽度限制。

# 分期建设计划（`app/phasing.py` / `app/plans.py`）

## 7. 人口权重与"不看权重"的不变量

居民点新增可选字段 `weight`（正数，缺省 1），表示该点代表多少人。
某一期"照顾到的人口"= 在该期已建站的服务半径内的居民点权重之和。

**最少开站求解完全不读权重。** 分期模块复用同一个
`app.solver.solve`，传入的掩码与权重相互独立；加权重前后来自求解器
的 `station_count / chosen` 一字不变（测试固化：诊所例加权后仍为
唯一最优 `{C1,C2,C3}`）。权重只进入排顺序那一步的人口计算。

## 8. 我们到底在优化什么（写在最前）

设 S_t 为第 t 期末已建集合，预算 b_t 为第 t 期最多新建站数。约束：

- S_0 ⊆ S_1 ⊆ … ⊆ S_{T-1}（已建不拆），
- |S_t \\ S_{t-1}| ≤ b_t，
- S_{T-1} 满覆盖全部居民点，必开集合 F ⊆ S_{T-1}。

声明目标是**词典序**：

1. **总站数 |S_{T-1}| 最少（第一优先）。** 有已确认期时，"最少"指
   在"已确认站不可更改"前提下的最少站数。这样早期安排永远是某个
   最少站方案的前缀，报告里"比无分期最少多几座"恒为 0（未证明路径
   除外，见 8.3）。
2. **在总站数最少的所有排法里，按期次顺序词典序最大化累计照顾人口
   向量** (pop(S_0), pop(S_1), …, pop(S_{T-1}))。末期恒为总人口。

### 8.1 为什么不是"每期贪当期最大"

纯贪心（每期独立选覆盖未覆盖人口最多的 b_t 座站）可能选出无法收进
任何最少站方案的站 —— 它前期好看，末期却要超建才能收口。我们明确
选择**先锁总站数、再在最少站方案集合里排顺序**，把"不多花总站数"
放在人口前面。

**代价（如实写明）**：允许超建的纯贪心可能在某一期给出更高的当期
人口；本目标在那种情形下宁可少照顾、也不多建站。返回体 `objective`
字段原文携带这段声明。

### 8.2 排顺序的精确搜索（非末期"恰好建满"是 WLOG）

- 先用求解器拿到最少站数 k* 与一个最少覆盖 K；
- 必开站不锁死在第 1 期，可以出现在任意一期（早建不亏，但交给搜索
  按人口安排）。可延展性检查 `ext_min(前缀, 自由名额)` 在"已合并全部
  必开站"的掩码上计算**还需额外开几座非必开站**：必开站强制建成、
  占该期新建名额但不进入自由补站计数；
- 非末期 t 枚举本期新建集合（大小 s 在"后期放得下剩余站"所要求的
  下界与预算上界之间）。少建是 WLOG 意义下可剪的：任何少建的可行
  排法，只要后期还有容量，就可以把后期的站前移到本期，前移不降低
  任何一期的累计人口（服务只增不减）。当后期容量吃紧时本期本来就
  必须建满；
- 每个候选前缀都做**可延展性**检查：`ext_min` 是带数量上限的集合
  覆盖子问题，用记忆化 DFS（分支在"可用覆盖者最少的未覆盖点"、
  最大覆盖反推下界剪枝）求精确最小自由补站数；加上未建必开站所占
  名额后必须放得进后期预算，且最终总规模恰好 k*（不多建）；
- **词典序乐观上界剪枝**：前缀已定时，对后续每期忽略站间重叠，用
  "边际人口最大的若干座站之和"给该期累计人口一个合法乐观上界
  （累计新增名额按 Σb 计算）；整条上界向量不优于当前最优向量即剪枝；
- 末期用 `ext_choice`（内部一个带回溯的小 DFS，受自由名额限制）
  重建补站集合，再并入未建必开站；
- 初始 incumbent 是一个贪心可行种子：逐期在"始终可延展"的前提下
  回溯凑足本期最少站数、再尽量多提前边际人口高的站，保证随时手上
  有合法计划可交出。

### 8.3 证明口径与时限

- 最少站数证明 + 排顺序搜索完整剪枝/穷尽 ⇒ `status=optimal`、
  `proven_optimal=true`。
- 到达时限：交出手上最好的**可行**计划，`status=feasible`、
  `proven_optimal=false`。若连求解器的最少站数都只拿到了超时 best
  （上界未证明），则候选宇宙被限制在该 best 覆盖集合内排顺序，且
  `minimum_stations / extra_over_minimum` 置 null，绝不拿上界冒充
  最少值。
- **收不了口绝不报成功**：
  - 全开也够不着某些点 ⇒ `status=infeasible`，列出这些点；
  - 最少站数已证明而任何预算序列都放不下（总容量不足，或已确认前缀
    占掉容量后剩余预算放不下，或新预算容不下已确认期）⇒
    `status=cannot_close`，给出 `blocked_period`（0 起；纯容量口径
    下收口失败发生在末期）、`budget_shortfall`，并在"尽量建满预算"
    后列出仍然够不着的居民点。
  - 未证明预算内是否可收口且到时限 ⇒ 仍为 `cannot_close` 但
    `proven_optimal=false`（不会伪装成成功，也不伪装已证明失败）。

## 9. 计划状态、逐期确认与并发（`app/plans.py` + `storage.plans`）

- 计划持久化在 `plans` 表，按
  `(version_id, radius, budgets JSON, forced JSON)` 幂等去重；
  同版本同参数重复发起取回同一记录，不产生重复。
- `confirmed_until` 记录已确认到第几期（-1 未确认）。只能顺序确认
  下一期；每次确认是一次
  `UPDATE ... SET revision=revision+1 WHERE id=? AND revision=?`
  的比较并交换（CAS）。
- 已确认期的新建站集合作为 `locked` 前缀喂给 8 的求解器：DFS 在这些
  层不分支、原样固定，最终结果再逐位断言一致。重排后期数必须多于
  已确认期数，且新预算要容得下每个已确认期，否则 409（不改动记录）。
- **并发**：确认与重排并发时只有一方 CAS 成功，另一方拿到
  409 + `field=revision` + `details.current_revision`，错误信息明确
  告知"计划已过时，请取回后重试"，不存在静默覆盖。

## 10. 旧库接管（存储升级）

- 新表以 `CREATE TABLE IF NOT EXISTS` 补齐，并置 `PRAGMA
  user_version=1`；挂载的旧数据目录无需清库。
- 旧居民点 JSON 没有 `weight`：读取版本时懒补 `weight=1.0`（不做
  一次性数据搬迁，避免不可逆地改写长期数据）。旧方案（solutions）
  原样可读、同参数继续去重复用；旧未完成作业启动时照旧标
  interrupted。
